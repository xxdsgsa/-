## 〇、全站灵魂

> **把重复琐碎交给 AI,把判断创造留给自己。代码是手段不是目的。**

作者原话的三段式:

| 交给 AI | 留给自己 |
|---|---|
| 重复琐碎 | 判断创造 |
| 苦活累活 | 品味思考 |
| 机械执行 | 灵感创意 |

配套的三条底线认知:

1. **想,都是问题;做,才是答案** —— 完美开局不存在,绝大多数成功产品都从简陋 MVP 起步
2. **代码是解决方案的最后一个环节** —— 项目始于问题,先有流程/规则/角色的方案,最后才轮到代码
3. **门槛降低了,天花板还在那,甚至更高** —— 你不必会写每行代码,但必须理解原理与边界(类比:不必懂手机相机的底层算法,但要知道光线太暗会拍糊)

作者对"谁才是老师"的判断:当技术迭代速度超过经验积累速度,前辈不再天然是权威。最先拥抱新技术的人天然承担带领他人的责任——**最危险的不是走错路,而是站在原地不动**。

### AI 时代一个人就是一支队伍

大厂流程 vs AI 时代的压缩:

| 阶段 | 大厂做法 | AI 时代(单人) |
|---|---|---|
| 需求 | PM 写文档 + 评审会 | 你写 PRD,让 AI 理解 |
| 技术设计 | 前后端分别出方案 + 评审 | AI 出方案,你审核调整 |
| 开发 | 分工编码 + 联调 | AI 写代码,你描述需求 + 查结果 |
| 测试 | QA 手动 + 自动化,来回打回 | AI 写用例,自动化跑 |
| 上线 | 合并 + 预发 + 灰度 5%→10%→50%→100% | 连仓库 + 一键部署 |
| 迭代 | 两周一迭代 | 以天甚至小时为单位 |

**但流程没有消失,只是被自动化了**。你仍需理解每个环节在做什么、为什么这么做、出了问题怎么排查。这正是本教程要教的。

## 一、环境与开发基础(第 1、4 章)

### 代码运行的三种状态

| 状态 | 类比 | 说明 |
|---|---|---|
| **Dev** | 打草稿 | 保存即热更新,方便调试。**不适合演示** |
| **Build** | 印刷成书 | 压缩优化代码 |
| **Production** | 正式出版 | 模拟正式环境,跑构建后版本 |

避坑:改了代码没效果 → 可能模式不对;别人看不到本地演示 → Dev 模式本来就不给别人看。

### 环境配置要点

- **nvm** 管理 Node 版本(不同项目不同版本)。国内下载慢要换镜像源
- **pnpm** 优于 npm:硬链接/符号链接共享依赖,**省 50%-70% 磁盘,速度快得多**。npm 是复制安装
- **文件夹命名**:必须用英文、不含空格/中文。底层工具对非英文字符支持差,**中文路径是各种离奇报错的根源**
- **模型 vs 工具**:模型决定能力上限,工具决定实现效率。国产模型(GLM 等)便宜且访问快,每月几十亿到数百亿 tokens 极具性价比——成本意识在 AI 原生开发中极重要

### Localhost 与端口

- `localhost` = `127.0.0.1` = "你自己的电脑"。发给朋友等于让他访问自己的电脑
- 端口 = 大楼里的房间号。一个端口同时只能容纳一个程序,冲突报 `EADDRINUSE`
- 开发时开多个项目会自动顺延到 3001、3002;生产环境规则严苛

### Dev / Build / Prod 对应命令

```bash
pnpm dev     # Dev:热更新
pnpm build   # Build:产出 .next/
pnpm start   # Production:跑构建产物
```

### 编程的四个基本构件

变量(存数据)、函数(封装可复用逻辑)、条件(分支)、循环(批量处理)。图灵完备的基础,任何可计算问题都能用它们组合解决。

### HTTP 四要素

每条请求指令 = 方法 + URL + Headers + Body。

**状态码速查(排错时最常用)**:

| 码 | 含义 | 典型场景 |
|---|---|---|
| 401 | 未认证 | 没登录/token 过期 |
| 403 | 无权限 | 登录了但无权访问 |
| 404 | 资源不存在 | 地址错或已删除 |
| 400/409 | 参数错/冲突 | 调用方的锅 |
| 5xx | 服务器内部错 | 服务器的锅 |

### 前后端职责

前端 = 浏览器里跑的代码,负责**展示**;后端 = 服务器上的代码,负责**处理**。

Next.js 让两者同项目同语言,但**职责没变**。作者强调模块化思维:不要把所有代码塞一个文件,拆成 `auth`/`api`/`components` 等模块。

### 配置文件格式

- **JSON**:`{}` 对象、`[]` 数组、"键: 值"。数字时代的普通话,跨语言通用
- **YAML**:无括号,用**缩进**表示层级,更简洁。多数 CI/CD 配置用 YAML

> 关键洞察:**对 AI 来说,结构清晰的格式(JSON/YAML/Markdown/Mermaid)比散漫的自然语言更像"标准说明书"**。这就是结构化文档能提升 AI 输出质量的原因。

### 集成外部 API 六步

获取凭证 → 选 SDK → 配环境变量 → 写最小测试 → **归档官方文档** → 处理常见错误

AI 应用推荐 **Vercel AI SDK** 的 `@ai-sdk/openai-compatible`:学一套规范,改 `baseURL`/Key/模型名即可调用全球主流大模型。

**测通后务必把官方文档存下来**,下次写功能直接喂给 AI,准确率显著提升。

## 二、AI 协作篇(第 2 章)—— 本项目日常最高频使用

### AI 编程的经济学

**Token 就是钱。上下文越大,花费越高。** 读整个项目 vs 只读一个文件是数量级差异。

优化提示词 ≠ 打磨话术,而是**减少 AI 需要读取的上下文范围**:
- 指定文件路径 > 模糊描述
- 指明功能范围 > "项目有问题"
- 删客套话、不设专家角色,直接说任务

> 精准上下文不仅省钱,输出还更准。

### Vibecoding 标准五步流

```
1. 探索项目结构  →  2. 规划实现步骤  →  3. 编码  →  4. 测试验证  →  5. 提交
```

听着像废话,但照做几次就会发现效率真的提高——**因为你不会写到一半才发现文件已经写过了**。

> **Vibecoding 的核心是 Workflow,不是 Prompt。**

### 三招让 AI 更好用

| 技巧 | 做法 | 解决什么 |
|---|---|---|
| **项目规则** | 根目录 `.iderules`/`AGENTS.md`,写"禁止 any""强制 pnpm" | AI 记性差、风格漂移 |
| **专属技能** | Skills,用自然语言定义 SOP | 重复流程反复解释 |
| **赋予能力** | MCP/插件,让 AI 连 GitHub 看代码、连数据库查数据、读 Figma | AI 只能在文本里打转 |

**给 AI 一个"出口"**:明确告诉它"如果不确定,就明说并等我确认,不要强行编造"。这是防幻觉最有效的一句话。

### Git 铁律

AI 编程非常激进——**可能为了修一个 Bug 而破坏三个旧功能**。

> "每当你完成一个独立功能的开发,或修复完一个 Bug 并验证通过后,请自动运行 git commit,并生成一句简洁的中文 commit message。"

### 调试心法

1. **给完整报错日志**。新手只复制最后一行是错的——AI 像医生,需要看完整症状。**原封不动全选复制**
2. **循环修复**。"我按你的方法改了,现在出现新错误……" 大多数 Bug 需 2-3 轮

### ⚠️ 危险信号:同一问题改 2-3 次没解决

**立即停下,人亲自定位根因。**

AI 缺乏元认知,会基于错误假设反复打补丁("按了葫芦起了瓢")。正确做法:明确告诉它**"你之前的假设是错的,真正的问题是 XXX"**。

## 三、产品思维与文档驱动(第 3 章)

### 产品验证三步法(写任何代码之前)

**第一步:灵魂三问**
- 用户是谁?—— 答"所有人"等于没有用户
- 痛点在哪?—— 答"我觉得需要"就不是真痛点
- 为何用你?—— 答"因为我们技术最好",用户根本不在乎

**第二步:MVP 思维** —— 能验证假设的最简版本是什么?例:外卖 App 的 MVP 可能是一个微信群 + 人工接单,而不是完整 App

**第三步:快速验证** —— 最小成本验证。手工服务或落地页收反馈都可以。**失败得越早,成本越低**

### 与 AI 确认需求:让它复述

AI **不会主动提问**。给模糊需求时,它会基于训练数据的常见模式做假设然后直接开写。

**主动确认模板**——每次讨论完让 AI 复述:
1. 目标用户是谁?
2. 核心功能有哪些?
3. **不做哪些功能?**
4. 可能有什么问题?

在写代码前发现误解,而不是等代码跑起来。

### PRD 五部分

| 部分 | 内容 | 对应阶段 |
|---|---|---|
| 一 | 文档信息:版本、阶段、干系人、版本历史 | 全程 |
| 二 | 需求背景与目标:项目概述、核心问题、用户故事、项目目标 | 初稿 |
| 三 | 方案概述:Mermaid 核心业务流程/功能流程/信息架构 | 中稿 |
| 四 | 细节方案:页面原型与交互、边缘 Case、非功能性需求 | 定稿 |
| 五 | 上线计划:排期、灰度发布策略 | 定稿 |

### PRD 三次迭代(作者强调"不是一蹴而就")

- **内部评审版(初稿)**:重点讲需求背景、目标、核心价值。不需要详细,把"**为什么做**"说清
- **项目评审版(中稿)**:补充核心业务流程图、功能流程图、原型交互说明。让开发/设计/测试都能看懂"**做什么**"
- **开发前定稿**:合入最终 UI 稿,补充边缘 Case、埋点方案、上线计划。详细到开发能照着做"**怎么做**"

> 每一版都有评审和修改,**避免到最后才发现大问题**。

### AI 的"阅读"方式

**AI 不会脑补,它严格按字面理解。** 有歧义就两条路:猜(可能错)或停下来问(增加轮次)。

推论——PRD 里必须显式写清:

| 不写会怎样 | 必须显式写 |
|---|---|
| 不写 Out-of-Scope → AI 按"企业级完整版"自由发挥,复杂度爆炸 | In-Scope / Out-of-Scope 清单 |
| 不写边缘情况 → AI 就不做 | 防抖、空状态、网络失败、超时 |
| 抽象词被误解 | "好看"→"白底蓝按钮无边框圆角";"流畅"→"0.5 秒内响应" |
| AI 编造事实 | 待定项标 **TBD** |

### 需求管理四工具

- **范围管理**:In-Scope / Out-of-Scope,管理预期,防范围蔓延
- **优先级排序**:表格列 需求ID / 模块 / 描述 / 优先级 / 状态
- **用户故事**:"作为\<角色\>,我想要\<任务\>,以便\<价值\>"
- **SMART 目标**:具体、可衡量、可实现、相关、有时限

### PRD vs 技术文档

| | 回答 | 内容 |
|---|---|---|
| **PRD** | 做什么 | 目标用户、核心功能、交互方式、边缘场景 |
| **技术文档** | 怎么做 | 技术栈、表结构、API 定义、第三方集成、部署方案 |

作者建议:不必拘泥形式,**可以合并为"项目文档"**,但必须清楚区分哪些是产品思考、哪些是技术决策。

> "写 PRD 不是形式主义,而是**训练你的问题定义能力**。很多人直接让 AI'帮我做个功能',来回改很多次。但先写清楚目标、用户、业务场景、交互逻辑,AI 往往一次就对了。**差距就在想清楚。**"

## 四、数据库篇(第 6 章)

### 从 JSON 文件到关系型数据库

- **JSON 文件**:最简单的持久化。帮你理解"数据库"的本质——**无非就是高效地读写硬盘上的文件**
- **关系型数据库**:数据多了要筛选(如"所有住北京且年龄>20"),遍历文件效率极低
  - **Table** = Excel Sheet;**Row** = 一条数据;**Column** = 属性
  - **Primary Key** = 唯一身份证,绝不重复
  - **Foreign Key** = 关联其他表的线索(如 `Orders.user_id` 顺藤摸瓜)

### 🔥 AI 交叉论证法(作者称之为"炼蛊")

判断 AI 设计的表结构好不好,新手看不出来。方法:

1. 让 **AI 1 号**设计表结构
2. 把生成的代码发给 **AI 2 号 / 3 号**,问:"作为一个资深数据库架构师,根据我的 PRD 和实际业务场景,这个设计合理吗?有什么潜在的性能隐患或逻辑漏洞?"
3. 通常**两轮左右"左右互搏"**就能得到健壮的模型

### Drizzle Schema 速读

```typescript
// src/db/schema.ts
import { pgTable, serial, text, timestamp, integer } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  id: serial('id').primaryKey(),           // 自增主键
  email: text('email').notNull().unique(),  // 必填且唯一
  name: text('name'),                       // 可选(不加 .notNull())
  createdAt: timestamp('created_at').defaultNow(),
})

export const posts = pgTable('posts', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  authorId: integer('author_id').references(() => users.id), // 外键
})
```

**类型选择要点**:
- `text` —— 文本。**永远用 text,不要用 varchar**
- `numeric` —— 精确小数,**金额必须用这个**
- `timestamptz` —— 带时区时间

> "数据库设计的关键是理解业务关系。AI 能处理技术实现,但'用户和订单是什么关系'需要你理解业务。"

### 三个核心概念

**CRUD** —— Create/Read/Update/Delete。不用写 SQL 也必须刻在脑子里,这是指挥 AI 操作数据的通用术语。

**事务(Transaction)** —— 多步数据库改动必须"打包"。例:转账从 A 扣钱给 B 加钱,扣成功但加失败数据就乱了。事务保证"**要么全成功、要么全失败**"。金融/订单类业务必备。

**索引(Index)** —— 书本目录。没索引全表扫描,有索引直接定位,**快几十到上千倍**。

> ⚠️ **索引不是越多越好**:占额外空间,增删数据时要同步更新,反而拖慢写入。通常只在"经常查询的字段"建。

> 🔥 **PostgreSQL 不会自动给外键列建索引——这是最常见的性能陷阱,必须手动加。**

### 数据校验:三道防线

| 防线 | 手段 | 定位 |
|---|---|---|
| 1. 数据库约束 | `.notNull()` `.unique()` `.references()` | **铁律**,代码有 bug 也拒绝违规数据 |
| 2. 后端 API 校验 | 邮箱格式、密码长度、枚举范围 | **主要防线**,数据入库前拦截 |
| 3. 前端表单验证 | `type="email"`、`required`、`min`、`max` | 仅体验(快速反馈免等网络) |

> **别因为有前端校验就省略后端和数据库保护——用户可以直接调 API 绕过前端。**

### 为什么是 PostgreSQL

最有说服力的例子:**OpenAI 的 ChatGPT 后端用的就是 PostgreSQL**,用单一主库支撑 8 亿用户,每秒处理百万级查询。

两个让 AI 开发者无法拒绝的特性:
1. **JSONB** —— 虽是关系型,却能像 NoSQL 一样直接存 JSON。**AI 生成的结构不确定的复杂数据可以直接丢进去**
2. **pgvector**(需单独装扩展)—— AI 时代的杀手锏,存储查询"向量数据",是 RAG(让 AI 回答时查阅你存的资料)的核心技术。**选 PG = 给未来 AI 功能铺路**

### Supabase vs Neon(作者明确倾向后者)

| | 定位 | 适合 |
|---|---|---|
| **Supabase** | 完整 BaaS:PG + Auth + Storage + Realtime + Edge Functions | 想快速验证 MVP、不想操心后端细节 |
| **Neon** | 专注数据库本身,无服务器架构,按需扩缩容 | **有自定义后端需求,想保持架构独立** |

作者建议:**用标准 PostgreSQL,不要被任何 BaaS 捆绑**。Supabase/Neon/Railway 都只是 PG 的不同托管方式,**你掌握的是数据库本身,不是某个服务平台**。

用 Drizzle 直连而非大量使用 Supabase 独有 SDK,才能保持迁移灵活性。换服务商只需改 `DATABASE_URL` 一个字符串。

### 数据备份(作者的"必修课")

> "数据是产品的灵魂,备份是开发的底线。"

**三件事**:自动备份(每天) + 多地备份(云+本地) + **定期恢复演练**。

> "太多人做了备份但从来没测试过,等到需要恢复时才发现备份文件损坏。**灾难恢复演练的重要性不亚于备份本身。**"

### 实战避坑

- **开发 vs 生产数据库**:学习阶段用一套快速上手可接受(部署时不用迁数据)。有真实用户后**强烈建议分离**,避免数据污染和安全风险
- **区分测试数据**:① 上线前手动清理;② 建表时加 `isTest`/`isDev` 字段,开发写入标 `true`,查询时过滤。删除测试数据时 `DELETE FROM users WHERE isTest = true` —— 一道安全闸门,不会误伤真实用户
- **连接字符串格式**:`postgresql://用户名:密码@主机:端口/数据库名`。任一标点错误或密码含特殊字符(需转义)都会失败,常报 `Invalid URL`

## 五、后端 API 篇(第 7 章)

### 为什么必须有后端

作者的关键反问:

> "前端代码运行在用户的浏览器里,如果前端直接连数据库,**用户打开 F12 就能看到你的数据库密码,还能随意删除别人的数据。**"

前端不能直连数据库——会暴露所有数据,也无法做权限控制。**API 是数据库的守门员,所有数据操作必须通过它。**

### 路由:URL 决定你看到什么

用豆瓣举例:`movie.douban.com/subject/37311135/comments?status=P` —— 路径参数标识"哪个资源",`?` 后是查询参数控制"怎么查"。

**Next.js 文件系统路由**——文件夹结构就是 URL 结构:

```
app/
├── page.tsx                    → /
├── subject/[id]/page.tsx       → /subject/37311135
└── chart/page.tsx              → /chart
```

`[id]` 是动态段。**创建文件就多一个页面**,不需要写配置文件。

**API 路由同理**:`app/api/movies/route.ts` → `/api/movies`。区别只是 `page.tsx` 返回页面,`route.ts` 返回 JSON 数据。

### 参数的三种来源

| 来源 | 例子 | 作用 |
|---|---|---|
| 路径参数 | `/subject/37311135` 的 `37311135` | 标识"哪个资源" |
| 查询参数 | `?status=P` | 控制"怎么查" |
| Request Body | 表单提交的 JSON(地址栏看不到) | 传递"要创建/修改的数据" |

### RESTful

用 URL 表示资源,HTTP 方法表示操作:`GET /api/movies`(列表)、`POST /api/movies`(创建)、`DELETE /api/movies/123`(删 id=123)。**看到路径就知道做什么。**

跟 AI 说一句"用 RESTful 风格",它会自动按这套规范来。

**tRPC 说明**:AI 生成的代码里可能出现 `trpc.movie.list()` 这类调用而非 `route.ts`——这是 tRPC,前端像调本地函数一样调后端。好处是**前后端类型自动同步**,改后端签名前端立刻类型报错。**和 REST 只是风格不同,解决同一个问题**,不用觉得奇怪。

### 统一响应格式(第一天就定)

```json
{ "success": true, "data": ... }
{ "success": false, "error": { "message": "..." } }
```

前端处理一致简单:先看 `success`,true 取 `data`,false 显错误。

### 你的工作 = 验证三件事

1. **跑起来了吗?** —— `pnpm dev` 启动,页面能正常操作
2. **数据库对吗?** —— 打开 Drizzle Studio 看数据是否正确写入
3. **报错了吗?** —— 终端报错整段复制给 AI

不需要读懂每行代码。**知道每个文件的职责,出问题时能告诉 AI"改哪个文件"就够了。**

传统 CSS 像写作文——给每个元素起名(`login-box`),在单独文件里描述。**容易撞名**:你叫 `card`,AI 也叫 `card`,两个样式打架。

Tailwind 允许直接在标签里写 `class="p-4 bg-red-500 rounded-lg"`。

> "这就好比 **AI 最擅长做填空题**,你让它'堆砌描述性的单词'比让它'管理复杂的文件引用'要准确得多。"

### shadcn/ui 为什么专为 AI 时代设计

### UX 三大避坑(附 AI 指令原句)

**1. 按钮反馈状态**
- ❌ 错误:点"支付"后页面毫无反应,用户以为没点上,疯狂点击 → **扣款两次**
- ✅ 指令:"请给这个提交按钮加上 Loading 状态。当用户点击后,按钮应变灰并显示转圈动画,且不可再次点击,直到请求结束。"

**2. 破坏性操作防护**

**3. 数据空状态**
- ❌ 错误:新用户注册进来页面一片空白,像出了 Bug
- ✅ 指令:"当列表没有数据时,不要留白。请展示一个可爱的插画组件,并放一个'创建第一个项目'的引导按钮。"

### 响应式设计

同一套代码按屏幕尺寸自动调整:手机单列、桌面双列;移动端隐藏次要信息。

## 七、安全与认证篇(第 8 章)

### 小明的 $127 教训

`git add .` 推了 `.env` → 10 分钟后 OpenAI 账单告警:**$127.43**,调用记录每秒几十次全是陌生请求。

**根因**:互联网上有成千上万自动化爬虫,24 小时不间断扫描 GitHub 上的每一次提交。它们不看代码好不好,**只找密钥**。

> **从密钥出现在公开仓库到被盗用,平均只需要 5 分钟。**

他删掉 `.env` 再推一次——**晚了**。
> "Git 记录了每一次提交的历史,你删掉的只是最新版本。任何人翻一下历史记录,密钥还在那里。"

后果:花一晚上重置密钥 + 清洗 Git 历史。如果泄露的不是 OpenAI Key 而是数据库密码,**用户邮箱、密码哈希、个人信息全部暴露**。

> "代码写得再好,密钥一泄露全白搭。**安全不是功能做完之后的锦上添花,而是从第一行代码开始就要考虑的。**"

### 密钥管理三件套

- **`.env`** —— 本地环境变量,**绝不提交**
- **`.gitignore`** —— 拦住 `.env`
- **`.env.example`** —— 当模板,告诉别人需要哪些变量

**云端环境变量要单独配**(见部署篇的头号踩坑)。环境变量是"代码和密钥之间的防火墙"。

### 为什么绝不自己写认证

认证是**安全领域最容易出错的部分**。自己写意味着要自己承担密码哈希、token 泄露、会话劫持、CSRF 等一整类风险。

**用成熟认证库(Better Auth)**:数据存自己库、TS 原生、插件覆盖注册验证码/找回密码。

### Session vs Token

| | Session | Token |
|---|---|---|
| 状态 | 服务端存 | 客户端存 |
| 撤销 | 立即可撤 | 难撤销 |
| **安全** | **HttpOnly Cookie 天然防 XSS 窃取** | 存 localStorage 可被脚本读取 |

> 🔥 **Token/Session 严禁写入 localStorage**——一旦有 XSS,任何脚本都能读走。必须用 **HttpOnly + SameSite Cookie**。

### 🔥 AI 应用特有安全问题

- **Prompt Injection** —— 用户输入可能包含"忽略之前的指令",诱导 AI 泄露系统提示或执行越权操作
- **成本攻击** —— 未授权用户用你的 Key 无限刷 API(小明的 $127)
- **幻觉内容** —— AI 生成的营养/健康建议可能错误,**健身类应用尤其致命**

> 健身/健康类应用:AI 输出必须标注为"仅供参考,不构成医疗建议",并在关键决策上加人工确认。

### 其他必修防护

- **SQL 注入** —— 一律用 Drizzle 参数化查询,**永远不拼接用户输入**
- **XSS** —— React 默认转义,慎用 `dangerouslySetInnerHTML`
- **CSRF** —— SameSite Cookie + 写操作校验 origin
- **依赖审计** —— `pnpm audit` 定期跑;本项目已用 overrides 打过补丁
- **行级安全(RLS)** —— 多用户数据隔离

### 权限控制:页面级 vs 接口级

- **页面级**:Middleware 统一拦截未登录用户跳转登录页(本项目 `proxy.ts` 已做)
- **接口级**:每个 API 内部再校验用户身份

> ⚠️ **两者都要有**。页面保护只是 UX,真正的防线在接口——用户可以绕过页面直接调 API。

### 🔥 所有用户数据查询必须带 user_id

这是最容易被 AI 忽略、后果最严重的一点。

> AI 在路由层很容易写出裸查询:`db.select().from(users)` —— 没有 `user_id` 条件。

**后果**:用户 A 只要改一下 URL 参数就能看到用户 B 的**全部数据**(体重、饮食、训练记录)。这是**越权访问漏洞(IDOR)**。

**防御**:
1. **收口** —— 所有查询统一走 `src/lib/db/queries/*`,不直接在路由里写 SQL
2. **强制条件** —— 每个查询函数的第一个参数就是 `userId`,并在函数内部拼进 where 条件
3. **E2E 验证** —— 写测试用 A 的 token 查 B 的数据,断言 403/404

## 八、测试篇(第 9 章)

### 小明的"打地鼠"困境

- 第二天:朋友说"搜索坏了" —— 他昨天只改了评分功能,但评分新加的查询函数**改了一个公共的数据库查询模块**,搜索也依赖它 → 被"误伤"
- 修好搜索后第二天:"详情页打不开了" —— 修搜索时不小心改了路由配置
- 当晚自测:评分功能本身又坏了

**三天三个 bug,每个都是修前一个时引入的。**

> 老师傅的话:"**你需要的不是更快的反应速度,而是一张安全网。** 想象一下,每次你改完代码,有个东西自动帮你把所有功能都检查一遍——搜索还能用吗?详情页还能打开吗?评分还正常吗?哪个坏了,它立刻告诉你。**你不用等朋友来报 bug,改完代码的那一秒就知道有没有误伤。**"

### 测试金字塔

**单元测试多、E2E 测试少而精。** 只测 2-3 条主流程。

AI 辅助测试的正确姿势:让 AI **生成测试用例**(覆盖边界情况),但**你来决定测什么**。不要追求覆盖率数字。

### 🔥 优先测统计计算

对 FitMate 这类应用,**营养汇总算错就是事故**——用户照着错的宏量营养配餐,直接危害健康。

**必须测的纯函数**(本项目已有):
- `nutrition.ts` —— 营养目标计算 + 摄入汇总
- `stats.ts` —— 周/月统计、完成率
- `account-calc.ts` —— 账号计算(体检数据)

> 温度写错顶多不准,**营养算错是健康事故**。这类纯函数必须 100% 覆盖。

### 每修一个 Bug 顺手加一个测试

这是把"打地鼠"变成"累积安全网"的唯一方法。修完 bug,立刻写一个测试锁住这个场景——下次回归立刻被发现。

### Git Hooks 与 CI

- **Git Hooks**(本地) —— commit 前自动跑测试和格式化
- **GitHub Actions CI**(云端) —— push/PR 自动跑测试

**同一个理念的两种形态**:"代码变更时自动触发操作"。本地 Hooks 跑测试格式化,云端 CI 跑构建部署,构成完整自动化闭环。

### zip 协作的困境

## 十、公网访问与部署(第 10、12 章)

### localhost 的本质

小明把地址栏的 `http://localhost:3000` 发给朋友,朋友回了个问号:"打不开啊?"

> "localhost 只有你自己能访问。你发给朋友的,等于让他访问**他自己的电脑**——他电脑上可没跑着你的项目。"

**三个网络层级**:

| 层级 | 地址 | 谁能访问 |
|---|---|---|
| localhost | 127.0.0.1 | 只有你自己 |
| 局域网 IP | 192.168.x.x | 同一 WiFi 下的人(真机调试用) |
| 公网域名 | https://xxx.com | 任何人 |

### 临时分享:内网穿透

**Cloudflare Tunnel** 等工具,不需要公网 IP 就能把 localhost 暴露出去。

⚠️ **注意事项**:隧道链接**关掉终端就失效**,不要用来做正式部署;**绝不暴露数据库端口**;隧道不要过夜(安全风险)。

### 部署平台对比

| 平台 | 访问速度 | 成本 | 难度 | 适合 |
|---|---|---|---|---|
| 腾讯云 EdgeOne Pages | 国内快 | 免费额度慷慨 | 简单 | **国内用户为主** |
| 阿里云 ESA | 国内快 | 免费额度充足 | 简单 | 国内项目 |
| Vercel | 国外快 | 免费版有限制 | 极简 | 海外用户或有域名 |
| Cloudflare Pages | 全球均衡 | 免费额度大 | 简单 | 全球用户 |
| GitHub Pages | 国外快 | 完全免费 | 最简 | 纯静态网站 |

> **国内项目优先 EdgeOne 或 ESA。**

### 数据库托管:Neon

专注 PG 本身,无服务器架构,按需扩缩容。**它就是标准 PostgreSQL**,用 Drizzle 通过标准连接字符串连接,**完全不涉及厂商捆绑**。换服务商只需改 `DATABASE_URL`。

### CI/CD = 自动化

**以前**:手动打包 → 传到服务器 → SSH 登录 → 重启服务
**现在**:
1. 本地 `git push`
2. GitHub 自动通知部署平台
3. 平台自动拉代码、装依赖、构建、发布

> **"保存即发布"。你不需要懂复杂的运维命令。**

### 部署配置四参数

| 参数 | 说明 |
|---|---|
| 框架预设 | Next.js,平台自动填推荐配置 |
| 根目录 | 代码位置,默认 `./` |
| 构建命令 | `pnpm build` |
| 输出目录 | Next.js 通常 `.next` |
| Node 版本 | 平台预装多个版本,**必须和本地一致** |

### 🔥 两个头号踩坑

**坑一:Node 版本不一致**
构建失败 → 日志显示 Node 版本太旧 → 在平台设置里把 Node 版本调成和本地一致 → 重新部署。

**坑二:环境变量失踪(最常见)**
构建成功了,但访问网页全是报错。原因:**`.env` 被 `.gitignore` 拦住了,GitHub 上根本没有你的数据库密码和 API Key**。

→ 在平台"环境变量"页面把本地 `.env` 内容逐条填进去(国内平台通常支持批量粘贴导入)。

> ⚠️ **环境变量的修改只对新部署生效,不会影响已有部署。**

**其他坑**:部署记录超过一定数量后旧的会被标记失效(省空间);预览链接在国内平台通常只有 3 小时有效期。

### CDN 与缓存三层

**CDN** = 全球各地部署缓存服务器,用户从最近的节点拿内容,而不是每次都回源站。像"在各地开了分店"。现代部署平台都内置,无需配置。

**缓存的三层防护**:

| 层 | 位置 | 你会怎么发现 |
|---|---|---|
| 浏览器缓存 | 用户本地 | 改了代码刷新还是旧的 → Ctrl+Shift+R 强刷 |
| CDN 缓存 | 全球节点 | 部分用户看到旧版本 |
| 服务端缓存 | 服务器内存 | **第一次打开慢,之后快,清了浏览器缓存也快** |

### 平台自动优化(不用你操心)

图片自动压缩、代码自动分割按需加载、静态资源分发到全球加速节点。

### 🔥 成本优化:分阶段,不要过早优化

| 阶段 | 用户量 | 策略 |
|---|---|---|
| MVP | < 1000 | Serverless 零成本起步,**不要过早优化** |
| 增长期 | 1000-10000 | 评估混合架构,成本增长过快再考虑自建 |
| 企业期 | > 10000 | 才需要为合规/性能自建服务器 |

> "**过早优化是万恶之源,不要在阶段一就担心阶段三的问题。**"

### AI 模型成本优化:智能路由

简单任务用便宜的国产模型(GLM、DeepSeek),复杂推理用 Claude。在代码里加判断层:简单翻译/摘要发给便宜模型,深度推理才发给 Claude。

作者案例:某 AI 应用通过**智能路由(70% GLM + 30% Claude),API 成本降低 80%**。

> "关键是**匹配任务复杂度和模型能力,不要用大炮打蚊子**。"

**免费额度陷阱**:免费额度只够测试用,一旦有真实用户费用会指数级增长。**记得设置账单告警**(如"超过 ¥70 发邮件提醒"),定期查看用量。

## 十一、域名、SEO 与合规(第 13、15 章)

### 免备案三板斧

想让国内用户流畅访问又不想备案:
1. 加速区域选"**全球不含中国大陆**"
2. 用 Vercel / Cloudflare(境外节点)
3. VPS 选**香港**地区

服务器在大陆**必须 ICP 备案**,2-4 周。

### SEO 三件套

- **Metadata** —— 在 `layout.tsx` 里配 `metadata` 对象,清晰的 `title` 和 `description`
- **Sitemap** —— 给爬虫的地图,告诉它有哪些页面、哪些最新
- **Robots.txt** —— 给爬虫的规则,哪些能爬哪些不能

SEO 不是一次性配置而是持续优化:结构化数据、Core Web Vitals、移动端友好度都是排名因素。

### Open Graph 分享(性价比最高的优化)

症状:把链接发到群里只显示一串蓝色文字,没标题没图,**根本没人想点**。

在 Next.js 里放一张 `opengraph-image.png`,**自动生成 OG 标签**,社交平台抓取时显示精美大图 + 引人入胜的标题。

> **OG 优化不是可选项,是营销的基础设施。** 视觉吸引力直接决定点击率。

### Umami 统计

Google Analytics 太重且容易侵犯隐私。**自建 Umami**(开源统计),贴一段 JS 代码即可。

> "**收集数据前先想清楚要解决什么问题。**" 有了数据才能做出更好的决策。

### 合规三件套(必修课)

1. **隐私政策** —— 收集用户数据(邮箱、行为数据等)必须有,说明用途、存储方式、用户权利。GDPR 不合规可能面临巨额罚款
2. **用户协议** —— 服务条款、免责声明、内容责任边界
3. **ICP 备案** —— 服务器在中国大陆必须做

> "合规是产品长期运营的基石。**不要等被举报了才想起来合规。**"

## 十二、用户反馈与迭代(第 16 章)

### 数据告诉你发生了什么,反馈才告诉你为什么

笔记软件团队花几个月开发"自动同步到云端"(他们觉得最重要),上线后才发现**用户最想要的是"离线也能查看"**——因为大部分用户在地铁、飞机上使用,根本没有网络。

> "你可能觉得自己很了解用户,因为**你就是用户之一**。但这样想很危险。你只是千千万万个用户中的一个。"

### 反馈收集渠道

| 渠道 | 适合收集 |
|---|---|
| 页面反馈按钮 | 具体 Bug 报告 |
| 邮箱 | 深度建议 |
| 社交群组 | 想法、讨论 |

**光有按钮不够** —— 用户不知道该说什么,要引导:"遇到了什么问题?想要什么功能?有什么建议?"

### 🔥 反馈优先级:两维度矩阵

**一、影响范围** —— 影响多少人?一个人遇到可能是个别情况,一半用户都遇到就是优先问题

**二、严重程度** —— 有多严重?"颜色不好看"用户还能继续用;"登录失败"用户根本用不了

综合排序:影响大且严重的优先。

### 用户访谈:让他们演示,不要问问题

❌ "你喜欢我们的产品吗?" → 大部分人会说还行(社交期望偏差)

✅ "**你上次使用时遇到了什么困难?**" → 让他们一边用一边说,你会观察到很多想不到的问题

**五到十个就够了** —— 因为你会反复听到同样的问题,这时候就知道真正的问题在哪了。

### 数据驱动决策

数据 + 反馈**两者对照**才能定位真问题。例:数据发现注册页流失率高 + 用户反馈"注册表单太长" → 对照后才知道要做的是简化注册流程,而不是加营销弹窗。

> "你不是拍脑袋做决定,而是根据数据和真实用户的反馈来**验证你的假设**。"
